# 基本設計書

## 1. システム概要

`cdbg` は macOS 上で動作する対話型 C デバッガである。`ptrace` と Mach カーネル API を組み合わせて debuggee を制御し、DWARF デバッグ情報を解析することで変数参照・ソース表示・ブレークポイントを実現する。

## 3. モジュール一覧

| モジュール | ファイル | 責務 |
|---|---|---|
| メインエントリ | `main.c` | 引数解析、`cdbg_t` 初期化、REPL 起動 |
| デバッガコア | `debugger.c` | REPL ループ、各コマンドの実処理（`cmd_*`）、ステップ制御、DWARF 変数/構造体解決、SIGINT ハンドラ |
| コマンド解析 | `cmd_lexer.l` / `cmd_grammar.y` | REPL 入力行の字句解析・構文解析（flex/bison）。認識したコマンドごとに `debugger.c` の `cmd_*` を呼び出す |
| 式 AST | `ast.h` / `ast.c` | 式の抽象構文木（`cdbg_ast_t`）のノード定義・生成・解放 |
| 式構文解析 | `ast_expr.l` / `ast_expr.y` | `print`/`set`/`watch` が受け取る式の字句解析・構文解析（flex/bison）。演算子優先順位は `%left`/`%right` で宣言 |
| 式評価器 | `ast_eval.c` | AST を右辺値として評価（`cdbg_ast_eval`）、または左辺値（アドレス+型）として解決（`cdbg_ast_resolve_lvalue`）。実際の変数/構造体解決は `debugger.c` の関数を呼び出す |
| 式評価 互換ラッパ | `expr.c` | `cdbg_expr_eval`（`debugger.h` 公開 API）を AST パーサ+評価器に委譲する薄いラッパ |
| プロセス管理 | `process.c` | fork/exec、`waitpid`、プログラムパス解決 |
| メモリアクセス | `memory.c` | Mach VM 読み書き（主経路）、ptrace 読み書き（フォールバック） |
| レジスタ操作 | `regs.c` | Mach スレッド状態取得・設定、PC/FP/SP 抽象化、フレームアンワインド、スレッド一覧取得（`cdbg_threads_list`）、スレッド一時停止/再開（`cdbg_thread_suspend`/`cdbg_thread_resume`） |
| ブレークポイント | `breakpoint.c` | トラップ命令埋め込み/復元（INT3 / BRK） |
| ウォッチポイント | `watchpoint.c` | ハードウェアデバッグレジスタの設定/解除（DBGWVR・DBGWCR / DR0-DR3・DR7） |
| シンボル管理 | `syms.c` | Mach-O シンボルテーブル解析、`nm` フォールバック、ASLR スライド算出 |
| 行番号管理 | `lineno.c` | DWARF line table 解析、PC ↔ ファイル:行 変換 |

`cmd_grammar.y` と `ast_expr.y` はそれぞれ独立した flex/bison ペアであり、生成コードの記号衝突を避けるため `%name-prefix`（`cmdyy` / `exprp`）でプレフィックスを分けている。

## 4. 状態機械

debugger は debuggee の状態を `cdbg_state_t` で管理する。

```
      run/spawn
  ┌─────────────────────────────────────────┐
  │                                         ▼
IDLE ◀────────────── exited/killed ──── RUNNING
  │                                         │
  │                                    waitpid停止
  │                                         │
  └──────────────── kill ──────────── STOPPED
                                            │
                           continue/step ───┘
```

| 状態 | 値 | 意味 |
|---|---|---|
| `CDBG_STATE_IDLE` | 0 | 対象プロセスなし |
| `CDBG_STATE_RUNNING` | 1 | 対象プロセス実行中 |
| `CDBG_STATE_STOPPED` | 2 | ptrace 停止中（ブレークポイント・シグナル等） |

## 5. 主要データ構造

### 5.1 cdbg_t（デバッガ中心構造体）

```c
typedef struct cdbg {
    pid_t            pid;                         // debuggee の PID
    cdbg_state_t     state;                       // 実行状態
    int              wait_status;                 // waitpid ステータス
    cdbg_regs_t      regs;                        // レジスタスナップショット
    uint64_t         current_tid;                 // 選択中スレッドの tid（CDBG_TID_PRIMARY=主スレッド）
    bool             thread_lock_active;          // lock 中かどうか
    uint64_t         locked_tid;                  // ロック対象スレッドの tid（thread_lock_active 時のみ有効）
    uint64_t         suspended_tids[64];           // lock が thread_suspend() した tid（unlock で resume）
    size_t           suspended_tid_count;
    cdbg_breakpoint_t breakpoints[64];            // ブレークポイント配列
    size_t           breakpoint_count;
    cdbg_watchpoint_t watchpoints[4];             // ウォッチポイント配列（HW スロット = 配列添字）
    size_t           watchpoint_count;
    cdbg_lineno_t    lineno;                      // DWARF 行情報
    cdbg_syms_t      syms;                        // シンボルテーブル
    char             executable_path[1024];
    char             debug_info_path[1024];       // dSYM パス
    char             run_argv_storage[64][1024];  // 実行引数ストレージ
    char            *run_argv[65];
    size_t           run_argc;
    bool             print_pretty;               // pretty print フラグ
    bool             malloc_stack_logging;        // MallocStackLogging フラグ
    cdbg_language_t  language;                   // 式評価言語
} cdbg_t;
```

## 7. ブレークポイント機構

### 設定

1. 対象アドレスの 1 バイトを `cdbg_mem_read` で退避
2. アーキテクチャ別トラップ命令を書き込む
   - ARM64: `0xd4`（BRK #0 の先頭バイト）
   - x86_64: `0xcc`（INT3）
3. `cdbg_breakpoint_t` に {addr, saved_byte, enabled=true, spec（元の `break` 引数）} を記録

### ヒット時

1. `waitpid` が停止を通知（macOS の ptrace はプロセス全体に対して作用するため、トラップしたのが `current_tid` と限らない）
2. `cdbg_threads_list` で全スレッドを列挙し、各スレッドの PC をブレークポイントアドレス群と照合する。一致するスレッドが見つかれば `current_tid` をそのスレッドに切り替える（`continue`/`step`/`si`/`next` のいずれから呼ばれても同じ経路で行う）
3. （切り替え後の）現在スレッドの PC を確認（x86_64 は INT3 実行後に PC が +1 されるため -1 補正）
4. トラップ命令を元のバイトに復元し PC を戻す
5. ブレークポイントを一時無効化 → シングルステップ → 再有効化

### `run`（再実行）との関係

`run` は新しいプロセスを fork/exec するため ASLR スライドが変わり、以前のプロセスに埋め込んだトラップ命令はそのままでは無効になる。`cdbg_breakpoint_t` は元の `break` コマンド引数（シンボル名・`file:line`・アドレス等）を `spec` として保持しており、`run` はブレークポイント配列を一旦クリアしたあと、新プロセスのシンボル・行情報・ASLR スライドが確定した時点で保存しておいた `spec` を `cmd_break` に再度渡し、新しいプロセスに対して再解決・再設定する。これにより「`run` 前に設定したブレークポイントは再起動後も保持される」という仕様を実際に満たす。

## 8. ウォッチポイント機構

ソフトウェアブレークポイント（命令埋め込み）ではなく、CPU のハードウェアデバッグレジスタを使用する。書き込みが発生するまでシングルステップせずフルスピードで実行できる。

### 設定

1. `watch [/r] [/1|/2|/4|/8] <expr>` で式のアドレスとサイズを解決（`print`/`set` と同じ lvalue 解決経路）。
   `/r` は読み取りもトラップ対象にし（省略時は書き込みのみ）、`/1`〜`/8` は監視サイズを明示指定する
2. サイズ明示指定がなければ 1/2/4/8 バイトに丸める（8 バイト超の構造体・配列は先頭 8 バイトのみ）
3. `task_threads` でタスク内の全スレッドを列挙し、各スレッドについて `thread_get_state` でデバッグレジスタを取得・該当スロットを書き換えて `thread_set_state` で書き戻す（1 スレッドだけでなく**全スレッド**に同じ内容を設定する）
   - ARM64: `DBGWVRn_EL1` / `DBGWCRn_EL1`（BAS フィールドでバイトオフセットを表現）
   - x86_64: `DR0`-`DR3` + `DR7`（R/W・LEN フィールドで監視サイズを表現、アドレスは自然境界にアライン必須）
4. アライメント等の理由で設定できない場合はサイズを半分にして再試行する（サイズ明示指定時はリトライしない）
5. 監視開始時点の値を `old_value` として保存

ウォッチポイントの配列インデックスがそのままハードウェアスロット番号になる（最大 4 個 = CPU のデバッグレジスタ数）。

デバッグレジスタはスレッドごとの状態であり、`pthread_create()` で生成されたスレッドはゼロクリアされた自分専用のレジスタを持つ。そのため 1 スレッドだけに設定していると、そのスレッド以外が監視対象を読み書きしてもトラップが一切発生しない。これを避けるため、上記の通り `watch` 設定時点で存在する全スレッドに同じ内容を設定するのに加え、`report_stop`（停止処理の共通経路）で毎回すべての有効なウォッチポイントを現在存在する全スレッドに設定し直す。これにより、ウォッチポイント設定後に新しく生成されたスレッドも、次に何らかの理由でデバッガが制御を取り戻した時点で追いつかせられる（ただし、スレッド生成通知の仕組みは無いため、生成から次の停止までの間に発生したアクセスは検出できない）。

### ヒット時

1. `waitpid` が停止を通知（ソフトウェアブレークポイントと同じ SIGTRAP 経由）
2. ヒットしたアドレスがソフトウェアブレークポイントのトラップと一致しない場合、各ウォッチポイントの現在値を再読み込みして `old_value` と比較する
3. 値が変化していれば、その時点の Old/New 値と停止位置を表示し、`old_value` を更新する

DR6/ESR のようなヒットスロットの直接デコードは行わず、値の前後比較のみで検出する（ハードウェアウォッチポイントの停止はアクセス完了後に発生するため、これで十分機能する）。

### 既知の制約

- ローカル変数のスタックアドレスを監視している場合、変数がスコープを抜けて同じアドレスが別の変数に再利用されると、無関係な書き込みを誤検出することがある
- 最大 4 個までしか同時に設定できない（CPU のハードウェアデバッグレジスタ数による制約）
- ウォッチポイント設定後に生成されたスレッドが、次の停止より前に監視対象へアクセスした場合は検出できない（スレッド生成イベントを捕捉する仕組みがないため）
- `/r`（読み取りもトラップ）指定時、`counter++` のような read-modify-write アクセスは読み出し側でトラップすることがあり、その時点では値がまだ変化していないため "Watchpoint hit" ではなく単なる "Stopped" として報告される（値の前後比較でヒット検出しているための制約）

## 10. シンボル・ASLR 対応

```
cdbg_syms_load()
  ├─ Mach-O をメモリマップ → __TEXT セグメントのリンク時ベースアドレスを取得
  ├─ nm コマンドでシンボルテーブルを文字列解析（第一優先）
  └─ 失敗時は Mach-O nlist_64 を直接パース

cdbg_syms_update_slide()
  └─ mach_vm_region_recurse で実行可能領域先頭を探索 → slide = 実行時先頭 - link_base

```

## 12. シグナル処理

```
SIGINT 受信（Ctrl+C）
  │
  ├─ state == RUNNING → kill(pid, SIGINT) で debuggee に転送
  │     → ptrace がシグナルを捕捉 → waitpid 復帰 → STOPPED 状態
  │
  └─ state != RUNNING（プロンプト待機中）
        → fgets が EINTR で中断 → clearerr + 改行 + プロンプト再表示

子プロセス分離:
  cdbg_process_spawn で setpgid(0, 0) を呼び、
  debuggee を独立したプロセスグループに移す。
  端末の Ctrl+C が両者に届かないよう分離した上で、
  シグナルハンドラが明示的に転送する。
```

## 14. コマンド解析・式評価アーキテクチャ

REPL の入力行解析と、`print`/`set`/`watch` が受け取る式の解析は、いずれも手書きの文字列走査ではなく flex（字句解析）+ bison（構文解析）で実装する。字句解析・構文解析という「文法」に関わる部分だけをパーサジェネレータに担わせ、DWARF 参照や構造体オフセット計算などの「意味解析」は従来どおり `debugger.c` の関数（`resolve_variable_address` 等）が担当し、両者を疎結合に保つ。

### 14.1 コマンド解析（`cmd_lexer.l` / `cmd_grammar.y`）

```
cdbg_repl():
  1 行読み込み → trim_space → 空行なら次のループへ
  cdbg_repl_dispatch_line(dbg, line)   ← ここから bison 側
    cmdyy_reset_state()                 // 直前の構文エラーで start condition が
                                         // ARGSTATE/WORDSTATE のまま残っていないことを保証
    cmdyy_scan_string(line)
    cmdyyparse(dbg, &outcome)           // %parse-param で dbg と結果を受け渡し
    cmdyy_delete_buffer(...)
  outcome (CDBG_REPL_OK / QUIT / FATAL) に応じて REPL ループを継続・終了
```

- 字句解析器は起動条件（start condition）を持つ：
  - `INITIAL`: コマンドキーワードを認識
  - `ARGSTATE`: 残り全体を 1 トークン（`RESTLINE`）として捕捉（`print`/`set`/`run`/`watch` 等、自由形式の引数を取るコマンド用）
  - `WORDSTATE`: 空白区切りで複数の `WORD` トークンを返す（`break`/`x`/`lines`/`syms` 等、単純な引数を取るコマンド用）
- 文法規則は「コマンドキーワード + （なし / WORD 0〜2個 / RESTLINE）」という形で各コマンドの引数形状を表現し、対応する `debugger.c` の `cmd_*` 関数（または `continue`/`step`/`kill` 等、REPL ループの制御フローを持つ `cdbg_repl_cmd_*` 関数）を呼び出す。
- 構文的に余分な引数（例: `break foo bar`）は bison の構文エラーとして拒否する。旧実装は `strtok` の呼び出し回数で暗黙的に無視していたが、新実装では明示的にエラーとする。

### 14.2 式解析（`ast_expr.l` / `ast_expr.y` / `ast.c` / `ast_eval.c`）

```
cdbg_ast_parse(text) → cdbg_ast_t*         // 構文解析のみ、意味解析はしない
cdbg_ast_eval(dbg, ast, &result)           // 右辺値として評価（算術式、変数読み取り、&/*、比較・論理演算）
cdbg_ast_resolve_lvalue(dbg, ast, &addr, &var)
                                            // 左辺値として解決（アドレス + cdbg_var_info_t 全体）
```

- 演算子優先順位は `%left`/`%right`/`%prec` 宣言で表現する（旧実装は `parse_logical_or` → … → `parse_primary` という再帰下降の関数チェーンで優先順位ごとに 1 関数ずつ手書きしていた）。
- `.`/`->`/`[]` の後置演算子チェーンは再帰的な文法規則になっているため、`a.b.c` や `p->q->r`、`arr[i+1]` のような多段アクセス・動的添字が自然にサポートされる（旧実装は `IDENT (.MEMBER | ->MEMBER | [NUMBER])` の 1 段のみで、添字も定数リテラルに限定されていた）。
- `print`/`set`/`watch` はいずれも同じ `cdbg_ast_parse` → `cdbg_ast_resolve_lvalue`（左辺値が必要な場合）/`cdbg_ast_eval`（右辺値でよい場合）の経路を共有する。旧実装は `print` 用に 3 段のフォールバック（裸の識別子専用パス／`resolve_lvalue` の文字列パーサ／`expr.c` の算術パーサ）を持っていたが、統一 AST により 1 回の構文解析＋種別判定に整理された。
- `cdbg_ast_resolve_lvalue` が失敗した場合、その原因（未知の変数・未知のメンバ等）は関数内で `stderr` に出力される。呼び出し側は「左辺値として解決できないノードだけ」算術評価にフォールバックする（`IDENT`/`MEMBER`/`ARROW`/`INDEX`/`DEREF` は必ず内部で `cdbg_ast_resolve_lvalue` を経由するため、左辺値解決に失敗したノードを算術評価に回しても同じ理由で必ず失敗する。二重にエラーメッセージを出さないよう、その場合はフォールバックしない）。

## 15. スレッド選択・スケジューリング制御（`threads` / `thread` / `lock` / `unlock`）

debuggee がマルチスレッドの場合、`regs`/`print`/`show locals|args`/`tb`/`up` はどのスレッドのレジスタ・スタックを見るかを選ぶ必要がある。`cdbg_t::current_tid`（`CDBG_TID_PRIMARY` = プロセスの先頭スレッド、それ以外は実スレッド ID）がこの「現在選択中のスレッド」を保持し、`regs.c` の全レジスタ取得/設定 API（`cdbg_regs_get`/`cdbg_regs_set`/`cdbg_regs_set_by_name`）が `pid` に加えて `tid` を引数に取ることで、常にこのスレッドを対象に動作する。

```
threads:
  1. cdbg_threads_list(pid) で task_threads() から全スレッドを列挙し、
     各スレッドの tid（thread_identifier_info）を取得
  2. 各スレッドについて cdbg_regs_get(pid, tid, &regs) で PC を読み、
     シンボル化して 1 行ずつ表示（現在スレッドには '*'、lock 中のスレッドには
     'L' を付与。両方に該当する場合は '*L' と両方表示される）

thread [n]:
  引数なし: 現在選択中のスレッドの番号・tid を表示
  引数あり: threads と同じ列挙結果の n 番目に current_tid を切り替え、
            cdbg_refresh_regs() でその場で dbg->regs を再取得し、
            print_stop_location で現在位置を表示する
```

- スレッド番号（`#n`）は `threads` 実行時点の列挙順に基づく一時的な番号であり、ブレークポイント/ウォッチポイント番号のように永続しない（スレッドの生成・終了で列挙順が変わりうる）。
- ハードウェアウォッチポイント（`watch`）は設定時点で存在する全スレッドのデバッグレジスタに対して設定され、`report_stop` のたびに全スレッドへ再設定される（詳細は「8. ウォッチポイント機構」）。ブレークポイントについても、ヒット時に全スレッドの PC を照合して実際にトラップしたスレッドへ `current_tid` を切り替える（詳細は「7. ブレークポイント機構」）。
- `run`（新規プロセス起動）および `kill`（デバッギ終了）はいずれも `current_tid` / `thread_lock_active` をリセットする（`current_tid` は `CDBG_TID_PRIMARY` に戻し、ロックは強制解除する）。

### スケジューリング制御（`lock` / `unlock` / ステップ実行）

`continue` は ptrace の `PT_CONTINUE` を使うため、プロセス全体（＝全スレッド）が一括で再開される（Linux の `PTRACE_CONT` と異なり、macOS の ptrace にスレッド単位の制御は無い）。特定のスレッドだけを動かしたい場合、ptrace とは独立した Mach の `thread_suspend()`/`thread_resume()` でスレッドごとの一時停止カウントを操作する。`thread_suspend()` されたスレッドは、たとえタスク全体が `PT_CONTINUE` で再開されても実行されない。

`step`/`si`/`next` も同じ `PT_STEP` ベースの制約を受ける。`PT_STEP` はカレントスレッドに 1 命令分のトラップを仕掛けるだけで、他スレッドを一緒に止めてはくれないため、特に `next` が「直接 call と認識できない呼び出し」（動的リンクされた関数への間接呼び出しなど）を1命令ずつの逐次シングルステップにフォールバックする場合、内部で `PT_STEP`+`waitpid` を多数回繰り返すことになり、その間ずっと他スレッドが実時間で動き続けてしまう。これを避けるため、`cdbg_step_next_line`/`cdbg_next_source_line`（`step`/`next` の本体）はループ開始前に `lock` と同じ `thread_suspend()` を現在スレッド以外の全スレッドへ適用し、`si` も含め処理が終わったら（成否・プロセス終了に関わらず）必ず `thread_resume()` で戻す。すでに `lock` でスレッドを固定中の場合は、二重に一時停止カウントを操作しないようこの処理をスキップする。

ループ開始前に 1 回だけ全スレッドを一時停止しても、それで十分ではない：`pthread_create()` のようにステップの**途中で新しいスレッドが生成される**場合、そのスレッドはループ開始時点ではまだ存在しないため一時停止の対象に入らない。放置すると、その新スレッドが自分自身のブレークポイント（0xCC/BRK）に実際に到達してしまうことがあり、これが「メインスレッドの `PT_STEP` 完了を待っている `waitpid()` に対して、別スレッドが無関係な SIGTRAP を発生させる」という状況を生む。検証の結果、この組み合わせでは `waitpid()` が完全にブロックしたまま二度と返ってこない（macOS の ptrace 実装の制約と見られる）ことを確認した。単発の `next` を何度も繰り返すと、体感で 1 割前後の頻度でこの無限ハングが再現した。

これを防ぐため、`cdbg_step_next_line`/`cdbg_next_source_line` はループの**各反復の先頭**で新規に現れたスレッドを検出し、即座に `thread_suspend()` する（`step_thread_guard_catch_up`）。1 反復＝1 命令分のステップ幅しかないため、新スレッドが生成されてから自分のブレークポイントに到達できるだけの猶予（通常はスレッド起動処理に相当の時間がかかる）よりも十分短く、実用上このレースを塞げる。

**`current_tid` が非プライマリスレッドの場合の制約**: `PT_STEP`/`PT_CONTINUE` は `current_tid` を一切参照せず、常にプロセスの**プライマリスレッド**のコンテキストに対して単一命令トラップを仕掛ける（`cdbg_regs_get`/`cdbg_regs_set` のように任意のスレッドを Mach API で明示的に指定できる仕組みとは異なる）。そのため、ワーカースレッドのブレークポイントヒットなどで `current_tid` がプライマリ以外に切り替わった状態で `step`/`si`/`next` を実行すると、実際にはプライマリスレッドが 1 命令進むだけで選択中のスレッドは進まない、あるいはカーネルがどのスレッドを「トレース対象」として保持しているかの状態次第で `waitpid()` が永久にブロックする、という 2 通りの不具合が非決定的に発生することを確認した（`libsystem_kernel.dylib` 内のシステムコール境界に着地するケースと `sample` でスタックトレースが `__wait4` に張り付くケースの両方を実際に観測）。

当初の一時停止ロジックは「`current_tid` 以外の全スレッド」を対象にしていたためプライマリスレッドまで一時停止してしまい、それが `PT_STEP` が実際に動かす対象を凍結してハングを引き起こしていた。一時停止対象からプライマリスレッドを常に除外する修正（`step_thread_guard_catch_up` が `is_primary` なスレッドをスキップ）を入れたところ、ハング頻度は下がったが、`current_tid` が非プライマリのまま `n` を連続実行すると依然として時々ハングすることを確認した（カーネル側がどのスレッドをステップ対象として認識するかが状況に依存するため、一時停止の有無だけでは解消しきらない）。最終的に、`current_tid` がプライマリでない間は `step`/`si`/`next` 自体を実行前に拒否し、"Cannot single-step: ... Run 'thread 0' ..." というエラーを表示して `thread 0` への切り替えを促す方式に変更した。`continue`・ブレークポイント・ウォッチポイントはタスク全体に対する再開／トラップなのでこの制約を受けず、非プライマリスレッドの状態確認自体は引き続き問題なく行える。任意のスレッドを個別に単一ステップさせる根本的な対応には、ptrace ではなく Mach の `thread_set_state` でハードウェアのシングルステップフラグを直接操作し、例外ポート経由でハンドリングする設計変更が必要で、現状は未対応。

```
lock <n>:
  1. state == IDLE → エラー、既に thread_lock_active → エラー（先に unlock が必要）
  2. cdbg_threads_list(pid) で列挙し、n 番目のスレッドを対象に決定
  3. 対象以外の全スレッドに cdbg_thread_suspend(pid, tid) を実行
     （途中で失敗したら、それまでに suspend したスレッドを resume してロールバックする）
  4. suspend したスレッドの tid を dbg->suspended_tids[] に記録
  5. dbg->thread_lock_active = true, dbg->locked_tid = 対象の tid
  6. dbg->current_tid も対象スレッドに切り替え、cdbg_refresh_regs() で dbg->regs を更新

unlock:
  1. state == IDLE → エラー
  2. thread_lock_active でなければ "Not locked." を表示して終了（エラーにしない）
  3. dbg->suspended_tids[] の各 tid に cdbg_thread_resume(pid, tid) を実行
  4. dbg->thread_lock_active = false, suspended_tid_count = 0
```

- `lock`/`unlock` は debuggee 側のスレッドスケジューリングにのみ作用し、`dbg->current_tid`（レジスタ閲覧対象）とは独立した状態（`thread_lock_active`/`locked_tid`/`suspended_tids[]`）で管理する。ただし利便性のため `lock <n>` は同時に `current_tid` も `<n>` に切り替える。
- 2 重ロック（既にロック中に別スレッドを `lock`）は許可しない。`unlock` してから改めて `lock` する。
